## 结论与解读

### 1. 批量发布仍然有效，但收益比早期记录的小得多

同一条队列、同样的搬运量，只改「每次 release store 发布多少帧」：

| 帧长 | batch=1 | batch=8 | batch=32 | 提速 |
|---|---:|---:|---:|---:|
| 1514 字节 | ~87 ns/帧 | ~73 ns/帧 | ~67 ns/帧 | **约 1.3 倍** |
| 64 字节 | ~15 ns/帧 | — | ~11 ns/帧 | **约 1.4 倍** |

原因不变：发布是一次 `release store`，会让写位置所在的缓存行跨核弹一次；
批量发布把这个固定成本摊薄成 `1/N`。

⚠️ **本节的倍数与本文档早期版本（2.4 倍 / 5.0 倍）对不上。** 差异来自机器换代 ——
早期数字测于另一台机器，本轮测于 Apple M5。M5 上跨核缓存行弹跳本身就便宜得多
（`batch=1` 从 ~134 ns 降到 87 ns），于是可被摊薄的部分变小了。
**结论方向没变（批量发布仍是净收益、仍应一律使用），但别再引用那两个倍数。**

> 实现见 `FrameRing::BatchWrite` / `BatchRead`。数据路径上**一律**用它们，
> 不要用逐帧的 `TryPush` / `BeginRead`。

### 2. 瓶颈确实是系统调用 —— 而且比原先估的还贵

本节此前用的 ~700 ns 来自调研的 `write(/dev/null, 1514)`，**不是**真实 BPF
描述符上的测量。现在有实测值了，而且**实测比估值贵约 3 倍**：

| 每帧工作 | 成本 |
|---|---:|
| RNDIS 编码（含 memcpy） | ~35 ns |
| RNDIS 解码（零拷贝） | ~1.8 ns |
| FrameRing 跨线程搬运（batch=32） | ~67 ns |
| 统计计数器 | ~0.34 ns |
| **合计 CPU** | **约 105 ns** |
| 一次 BPF `write()`（逐帧，**实测**） | **约 2180 ns** |
| BPF 批量写摊到每帧（≥32 帧，**实测**） | **约 805 ns** |

**逐帧系统调用是 CPU 成本的 20 倍以上**，批量写之后仍有 8 倍。这解释了架构里
几乎所有关键决定：

- RX 用 `BIOCSBATCHWRITE` 一次系统调用发整批；
- TX 用 RNDIS 多包聚合，让一次 bulk OUT 承载多帧；
- 在 `INITIALIZE_MSG` 里把 `MaxTransferSize` 报大（默认 16 KiB 而非 Linux 的
  2048），这是让**设备**把多帧聚合进一次 bulk IN 的唯一手段；
- 绝不用 kqueue 做轮询。

### 3. BPF 写入的成本几乎与帧长无关 —— 所以批量写才这么关键

| 写法 | 1514 字节 | 64 字节 |
|---|---:|---:|
| 逐帧 `write()` | 2181 ns | 1934 ns |
| 批量 32 帧 | 805 ns/帧 | ~728 ns/帧（batch=64） |

64 字节帧只比 1514 字节帧便宜 **13%**，而数据量差了 23 倍 —— 说明这笔开销
**几乎全是每次调用的固定成本**（陷入内核、取 BPF 描述符锁、走 `bpf_movein`
与接口输出路径），与实际搬运的字节数基本无关。

批量写的收益在 **batch=32 就饱和**（32/64/128 帧分别是 805 / 854 / 841 ns/帧，
差异已落进噪声）。再往上加批量只是增加延迟，不再换来吞吐。

**这条同时给出了一个安心的结论**：批量写下 805 ns/帧 ≈ 124 万帧/秒，
1514 字节时约 15 Gbps —— 而 USB 2.0 高速满速也只需约 2.7 万帧/秒。
**BPF 写入远不是本项目的瓶颈**，哪怕退回逐帧写（46 万帧/秒）也还有 17 倍余量。
早先「BPF 写入决定 RX 方向理论上限」的担心可以放下了。

### 4. feth 数据路径的往返延迟约 24 µs

从驱动侧 BPF 写一个 ARP 请求，到读回系统侧 IP 栈的 reply，中位数 **24.5 µs**。
这里面包含两次 BPF 系统调用、feth 对的两次穿越、以及对侧 IP 栈处理 ARP 的时间。
作为对比，真机上主机 ↔ 手机的 ICMP 往返是 **约 400~600 µs**，即 feth 这一段
只占端到端延迟的 **约 5%** —— 延迟的大头在 USB 与设备侧，不在虚拟网卡。

### 5. 聚合度对编解码本身几乎没有影响

RNDIS 编码在「每传输 1 / 4 / 10 帧」下是 35.1 / 35.5 / 36.6 ns/帧，
解码是 1.8 / 2.0 / 2.3 ns/帧。也就是说**聚合的收益全部来自减少系统调用与 USB
往返，而不是省 CPU**。对齐要求（`PacketAlignmentFactor`）让编码从 36.6 涨到
39.1 ns（多一次 memset 与 MessageLength 回填），约 7%，可以忽略。

### 6. 解码是零拷贝的，它的「吞吐」不可与编码比较

解码器只解析头部并返回指向传输缓冲内部的视图，**一个字节都不搬**，因此表格里
它的吞吐列刻意留空（`—`）。如果硬给它算 Gbps 会得到上万这种荒谬数字。
编码那边是真的在 memcpy 整帧，两者的 ns/op 可比，Gbps 不可比。

### 7. relaxed load+store 比 fetch_add 快 6 倍

统计计数器用 `relaxed load + store`（0.34 ns）而非 `fetch_add`（2.04 ns）。
差距来自 arm64 的 LSE 原子指令 `ldadd` —— 它必须获得缓存行的独占所有权。
因为每个计数器只有唯一的写线程，我们不需要读-改-写的原子性。

每帧省下的 1.7 ns 本身微不足道；真正的价值在于**避免两个方向的计数器争抢同一条
缓存行** —— 一旦跨核争用，成本会从 2 ns 跳到 60 ns 以上。

### 8. 未对齐读取零代价

解析 44 字节 RNDIS 包头（11 次 `LoadLe32`，刻意放在奇数偏移上）约 1.03 ns，
即约 0.09 ns/字段。证实了 `byte_order.h` 里「`memcpy` + `byteswap` 会被 clang
优化成单条 `ldr`」的说法。

## 真机端到端实测

**被测设备**：vivo iQOO Z10x（型号 V2445A / PD2445M），Android 15（SDK 35），
USB `2d95:600b`，RNDIS 接口签名 `e0/01/03`（无线类变体），协商为 **USB 2.0 高速**。
手机侧 iperf3 3.21 为用 NDK r28 交叉编译的静态 arm64 二进制；主机侧 iperf3 3.21。
MTU 1500，测试期间手机作为网关（`rndis0` = 192.168.35.7/24）。

| 方向 | TCP | UDP（灌入 250 Mbit） |
|---|---:|---:|
| **RX**（设备 → 主机） | **324~327 Mbps**，**0 重传** | — |
| **TX**（主机 → 设备） | 234~241 Mbps，数千次重传 | 交付 142~161 Mbps，**丢 35~43%** |

USB 2.0 高速下 RNDIS 的有效载荷理论上限约 **426 Mbps**，RX 方向达到了它的 **77%**。

### 三条实测结论

**① RX 干净，TX 是弱侧。** RX 在所有配置下都稳定在 ~325 Mbps 且零重传、零丢帧；
TX 在同样的链路上只能到 ~235 Mbps，且伴随数千次 TCP 重传。

**② TX 的丢帧发生在 TetherKitNext 自己的 TX 路径上，不是设备拒收。**
运行时统计直接给出证据（`--tx-transfers 4`，默认值）：

```
TX 20213 pps / 244.82 Mbps（丢 1889）  |  队列深度 0  内核丢包 0  背压 1155
```

`丢` 与 `背压` 同步增长，说明 BPF 读上来的帧因为拿不到空闲的 bulk OUT 传输而被丢弃。
**根因与修复见下一节** —— 简言之：桥接层在传输池占满时立即丢弃批次剩余帧，
而它本该等几百微秒。

**③ TX 的问题不是 RNDIS 多包聚合。** 本机 Android 汇报
`MaxPacketsPerMessage=10`，一度怀疑设备其实只拆第一个包（主线 Linux gadget 的
`rndis_rm_hdr()` 正是每次只拆一个）。用新增的 `--max-tx-packets` 做 A/B 后
**该假设被证伪**：

| 每传输聚合包数 | UDP 丢包率 | TCP TX |
|---|---:|---:|
| 1（钳死） | 42% | 125 Mbps |
| 3 | 43% | 237 Mbps |
| 10（设备汇报值，默认） | 35~58% | 234~241 Mbps |

钳到 1 反而**更差**。聚合是有效的，问题在别处（见 ②）。

### 双向并发时 TX 曾塌陷到 4.8 Mbps

修复前，单向各自正常，但同时跑双向 TCP 时：

```
[TX-C]  4.82 Mbits/sec   471 retr   cwnd 11.3 KBytes
[RX-C]  320  Mbits/sec     0 retr
```

TX 塌到 **4.8 Mbps**，约为单向时的 1/50。当时的机理分析是**缓冲膨胀**：

- 用 UDP 复测排除了 USB 带宽争抢 —— RX 满载时并发灌 50 Mbit UDP，TX 丢包只有
  **0.32%**，两个方向合计 348 Mbps 都正常；
- 但 RX 满载会把往返时延从空闲时的 **0.4 ms 抬到 16.6 ms**（40 倍）；
- TX 流的 ACK 要走这条被塞满的 RX 路径回来，于是 cwnd 卡在 11 KB，
  `11 KB × 8 / 16.6 ms ≈ 5.3 Mbps` —— 与实测的 4.8 Mbps 吻合。

这个算式是对的，但它只解释了**后果**。真正的第一因是 cwnd 为什么会卡在 11 KB ——
是 TX 侧在丢帧。把丢帧修掉之后，双向 TX 从 4.8 直接回到 **87 Mbps**，
而 RTT 膨胀本身并没有被处理。**所以 bufferbloat 是次要因素，不是根因。**

## TX 丢帧的根因与修复

**根因**（一行）：`Bridge::RunTransmitExtractor` 在 USB 传输池占满时**立即丢弃**
本批剩余帧，而它本该等几百微秒。

旧代码在 `SendFrames` 返回 0 时执行 `AddDroppedFull(剩余) + break`，附了一条
理由充分得很有说服力、但事实错误的注释：

> 这里刻意**丢弃**而不是等待：等待会让 BPF 的内核缓冲堆积，最终由内核丢包
> （而且是我们看不见的丢包）。在用户态丢并计数，运维才知道发生了什么。

两处都不成立：

1. **内核丢包并非「看不见」。** `BpfLink::ReadFrames` 每一批都读 `BIOCGSTATS`
   把 `bs_drop` 带回来，它就显示在统计行的「内核丢包」列里。
2. **内核缓冲正是该吸收突发的那一级。** 默认 4 MiB，在 250 Mbps 下约等于
   130 ms 的弹性；而传输槽位的实际释放周期只有几百微秒（一次 bulk OUT 的完成
   时间）。旧代码一微秒都不肯等，把本该由 4 MiB 缓冲吸收的突发直接丢在了
   用户态。

量级对不上得很离谱：设备汇报 15800 字节 / 10 包，一个 256 帧的提交分片需要约
**26 个传输槽**，而池里只有 **4 个**。于是每个分片必然在第 4 个槽之后撞上背压，
剩下 200 多帧当场丢弃 —— 这就是那 30%+ 的 TX 丢包率。

**修复**：`SendFrames` 改为返回 `SendOutcome{consumed, sent_frames, sent_bytes,
skipped}`；桥接层在 `consumed == 0` 时调 `WaitForSendCapacity(50ms)` 等槽位
（由完成回调用条件变量唤醒），醒来后回到循环顶部重查停机/暂停标志再重试，
**一帧都不丢**。溢出兜底交还给内核 BPF 缓冲，它满了才丢、且丢在统计里可见。

### 修复效果（同一台设备，默认参数）

| 指标 | 修复前 | 修复后 |
|---|---:|---:|
| TetherKitNext 自己的 TX 丢帧（6~8 秒窗口） | 1889 | **0** |
| TCP TX 重传 | 3829 | **0** |
| TCP TX 吞吐 | 234~241 Mbps | 239~302 Mbps |
| **双向并发 TX** | **4.8 Mbps** | **87 Mbps** |
| 双向并发 RX | 320 Mbps | 240 Mbps |
| 单向 TCP RX（回归检查） | 324~327 Mbps | 326~327 Mbps |

两点必须诚实说明：

- **双向 RX 从 320 降到 240。** 这不是退步而是公平性恢复：修复前 TX 被饿死到
  4.8 Mbps，RX 独占了链路；现在两个方向各得其所，合计从 325 Mbps 变成
  约 327 Mbps —— 总量没变，分配变了。
- **TCP TX 是双峰的**（约 240 或约 300 Mbps，两个稳定态），三次重复里都能看到
  两种值。原因未查明，但两种状态都是零重传，不是丢包造成的。

修复前把在飞传输数从 4 提到 16 能把丢帧降到约 1/4，那是在拿池深度补偿
「不肯等待」这个缺陷。修复后重复三次实测：

| `--tx-transfers` | TCP TX（3 次） | 双向 TX | TCP RX |
|---|---|---:|---:|
| 4（默认） | 239 / 297 / 241，重传 0 | 87.8 / 86.6 | 327 |
| 8 | 298 / 238 / 297，重传 0 | 86.9 / 85.7 | 326 |
| 16 | 302 / 302 / 217，重传 1 | 86.2 / 89.6 | 326 |

**三档没有可分辨的差异。** 默认值因此保持 4 —— 池深度本来就不该是吞吐的杠杆，
它只需要够让「组装下一批」与「上一批在飞」重叠起来。

### 一个必须记住的排查陷阱：Android 的 `rx_errs` 计数器不可信

手机侧 `/proc/net/dev` 的 `rndis0` 会在 `rx_errs` / `rx_frame` 上疯狂计数
（实测一度占到收包数的 30~50%），很容易被当成「主机发的帧是坏的」。**它不是。**
用低速率对照实验可以立刻证伪：

```
50 个 ping → 50 个回应，0% 丢包；但 rx_pkts +51 的同时 rx_errs 也 +51
```

每一帧都同时被计入「收到」和「错误」，而应答完全正常。
**排查 TX 问题时请以 iperf3 的实际丢包率与 TetherKitNext 自己的统计为准，
不要用手机侧的 `rx_errs`。**

## 测量方法与已知局限

- **微基准的数字都是 L1 常驻的上界。** 真实 RX 路径的源是 USB DMA 刚写入的缓冲，
  对 CPU 缓存是冷的；调研给的流式 memcpy 实测是 67~71 ns/1514 字节，
  而本文表格里的热缓存 memcpy 是 ~33 ns。请把表里的 CPU 侧数值当作**下界**。
  链路层那一组（BPF / feth）不受此限 —— 它测的是真实系统调用。
- **「RNDIS 编码比裸 memcpy 还快」这个历史疑点已经消失。** 本文早期版本记录过
  一个无法解释的偏差：编码 1514 字节测出 ~14 ns/帧，比 `memcpy` 1514 字节的
  ~25 ns 还快。本轮在 Apple M5 上复测，编码 35.1 ns / memcpy 32.9 ns ——
  编码**略慢于** memcpy，符合直觉（它就是 memcpy 加一个 44 字节头）。
  该偏差应归因于早期那台机器的访存行为，现已不复现，不必再追。
- **离散度偏高的项**（`SPSC 跨线程搬运`、`FrameRing 单线程往返（64 字节）`、
  `feth 往返延迟`）应看**最好轮**。原因是自旋线程可能被调度到性能核或效率核的
  不同组合上（本机 4 P + 6 E），而 macOS 不提供绑核接口
  （`thread_affinity_policy` 在 Apple Silicon 上基本无效）。
- **链路层基准需要 root**，非 root 运行时该组不会静默消失，而是在报告里留下
  「本次未测量」的说明。重新测量：`sudo ./build/bin/tetherkitnext_bench > docs/BENCHMARKS.md`。
  注意夹具必须在 `main` 返回前显式拆除（`ShutdownNetBenchmarks`）—— 留给静态析构
  会因日志互斥量已被销毁而抛异常，表现为「基准全跑完了但退出码是 134」。
- 曾经踩过的一个测量错误：统计计数器最初测出 **0.00 ns/op**，因为 relaxed 原子的
  连续读-改-写**允许**被编译器合并（N 次 +1 折叠成一次 +N）。加 `ClobberMemory`
  编译屏障后才得到真实的 0.34 ns。所以本项目的每个基准都必须自问一句
  「被测的工作真的发生了吗」。

## ⚠️ 压测环境的一个陷阱：提权链会吞掉 SIGTERM

`osascript ... with administrator privileges` 这条提权链**会吞掉进程间的 SIGTERM
投递**：脚本里 `kill -TERM $pid` 返回 0、目标进程的 `blocked` / `pending` 掩码都是 0、
`sigaction` 装的 handler 也确实在位（`sample` 能看到 handler 地址不是 `SIG_IGN`），
但信号永远不会到达，进程只能 `kill -9`。

用一个 15 行的 C 程序做过对照，与 TetherKitNext 无关：

| 执行环境 | 收到 SIGTERM？ |
|---|---|
| 普通 shell | ✅ |
| 普通 `osascript do shell script` | ✅ |
| `osascript ... with administrator privileges` | ❌ |

**后果：别用这条链验证优雅停机**，它会造出一个「停机卡死」的假故障，而且跟被测
代码毫无关系 —— 修复前后的运行日志里都是清一色的 `Killed: 9`。要验证端到端停机，
在真正的终端里 `sudo build/bin/tetherkitnext-cli` 再 Ctrl-C（已如此验证，见上）。
