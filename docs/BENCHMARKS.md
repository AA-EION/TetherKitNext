## Key Findings and Analysis

### 1. Batch Publishing Remains Effective, Though the Gain Is Smaller on Newer Silicon

Using the exact same ring and payload volume while varying only how many frames are published per `release store`:

| Frame Size | batch=1 | batch=8 | batch=32 | Speedup |
|---|---:|---:|---:|---:|
| 1514 bytes | ~87 ns/frame | ~73 ns/frame | ~67 ns/frame | **~1.3×** |
| 64 bytes | ~15 ns/frame | — | ~11 ns/frame | **~1.4×** |

Why: publishing performs a `release store` that bounces the cache line holding the write index across cores; batch publishing amortizes that fixed cost by `1/N`.

⚠️ **These speedup ratios differ from earlier numbers (2.4× / 5.0×) recorded on an older machine.** On Apple M5, cross-core cache-line transfers are significantly faster (`batch=1` dropped from ~134 ns to 87 ns), leaving a smaller fixed overhead to amortize. **Batch publishing remains a net win and should always be used (`FrameRing::BatchWrite` / `BatchRead`) on the data path.**

### 2. The Bottleneck Really Is System Calls — and They Are Pricier Than Estimated

Earlier estimates of ~700 ns came from `write(/dev/null, 1514)` rather than a real BPF file descriptor. Real BPF measurements show **per-frame writes cost ~3× more than estimated**:

| Per-Frame Operation | Cost |
|---|---:|
| RNDIS encode (including `memcpy`) | ~35 ns |
| RNDIS decode (zero-copy) | ~1.8 ns |
| `FrameRing` cross-thread transfer (batch=32) | ~67 ns |
| Stats counter | ~0.34 ns |
| **Total CPU** | **~105 ns** |
| Single per-frame BPF `write()` (**measured**) | **~2180 ns** |
| Amortized BPF batch write (≥32 frames, **measured**) | **~805 ns** |

**A per-frame syscall is more than 20× the total CPU cost**, and even with batch writes it remains ~8× the CPU cost. This explains every major architectural decision:

- RX uses `BIOCSBATCHWRITE` to deliver an entire batch in one syscall;
- TX uses RNDIS multi-packet aggregation so one bulk OUT transfer carries multiple frames;
- `INITIALIZE_MSG` advertises a large `MaxTransferSize` (default 16 KiB instead of Linux's 2048) so the **device** can pack multiple frames into each bulk IN transfer;
- `kqueue` is never used for polling.

### 3. BPF Write Cost Is Nearly Independent of Frame Size — Making Batching Essential

| Method | 1514 Bytes | 64 Bytes |
|---|---:|---:|
| Per-frame `write()` | 2181 ns | 1934 ns |
| Batch of 32 frames | 805 ns/frame | ~728 ns/frame (batch=64) |

A 64-byte frame is only **13% cheaper** than a 1514-byte frame despite carrying 23× less data — proving that the cost is **almost entirely fixed per-syscall overhead** (kernel entry, BPF descriptor lock acquisition, `bpf_movein`, and DLIL output path traversal) rather than byte copying.

Batch write speedup **saturates around `batch=32`** (805 / 854 / 841 ns/frame for 32 / 64 / 128 frames, well within noise). Larger batches only add latency without improving throughput.

**Reassuring implication**: 805 ns/frame under batch write equates to ~1.24 million frames/sec (~15 Gbps at 1514B), whereas saturating USB 2.0 high-speed requires only ~27k frames/sec. **BPF writing is nowhere near being a bottleneck** — even falling back to per-frame writes (~460k frames/sec) leaves a 17× safety margin.

### 4. `feth` Data-Path Round-Trip Latency Is ~24 µs

Writing an ARP request into the driver-side BPF fd and reading back the ARP reply from the host IP stack takes a median of **24.5 µs** (covering two BPF syscalls, two traversals of the `feth` pair, and kernel ARP processing). By comparison, real host ↔ phone ICMP RTT is **400–600 µs**, meaning the `feth` virtual interface pair accounts for only **~5%** of end-to-end latency.

### 5. Aggregation Factor Has Negligible Impact on Codec CPU Cost

RNDIS encoding at 1 / 4 / 10 frames per transfer takes 35.1 / 35.5 / 36.6 ns/frame, and decoding takes 1.8 / 2.0 / 2.3 ns/frame. **All benefits of aggregation come from reducing syscalls and USB round-trips, not saving CPU.** Enforcing 128-byte `PacketAlignmentFactor` padding increases encoding time from 36.6 to 39.1 ns (~7%), which is negligible.

### 6. Decoding Is Zero-Copy; Its "Throughput" Is Not Comparable to Encoding

The decoder only validates headers and returns `std::span` views into the transfer buffer without copying a single payload byte. Therefore, the throughput column for decoding is intentionally left blank (`—`).

### 7. Relaxed `load+store` Is 6× Faster Than `fetch_add`

Stats counters use `relaxed load + store` (0.34 ns) rather than `fetch_add` (2.04 ns). On arm64, `ldadd` requires exclusive cache-line ownership; since each counter has a single writer thread, atomic read-modify-write is unnecessary and avoids cross-core cache-line contention.

### 8. Unaligned Reads Are Free

Parsing a 44-byte RNDIS packet header (11 `LoadLe32` calls deliberately placed at an odd byte offset) takes 1.03 ns (~0.09 ns/field), confirming that Clang compiles `memcpy` + `byteswap` into a single `ldr` instruction.

## End-to-End Real-Device Measurements

**Device under test**: vivo iQOO Z10x (V2445A / PD2445M), Android 15 (SDK 35), USB `2d95:600b`, RNDIS interface signature `e0/01/03` (wireless class variant), negotiated at **USB 2.0 High-Speed**. Phone-side `iperf3` 3.21 cross-compiled as a static arm64 binary with NDK r28; host-side `iperf3` 3.21. MTU 1500, phone acting as gateway (`rndis0` = `192.168.35.7/24`).

| Direction | TCP | UDP (250 Mbit offered load) |
|---|---:|---:|
| **RX** (Device → Host) | **324–327 Mbps**, **0 retransmits** | — |
| **TX** (Host → Device, pre-fix) | 234–241 Mbps, thousands of retransmits | 142–161 Mbps delivered, **35–43% loss** |

The theoretical RNDIS payload limit over USB 2.0 High-Speed is **~426 Mbps**; RX achieves **77%** of the theoretical ceiling.

### Three Empirical Conclusions

**① RX was clean; TX was initially the weak side.** RX consistently achieved ~325 Mbps with zero retransmissions and zero frame drops across all configurations, whereas TX initially reached ~235 Mbps with heavy TCP retransmissions.

**② The TX frame drops occurred inside TetherKitNext's own TX path, not on the device.**
Runtime statistics (`--tx-transfers 4`) revealed the smoking gun:

```
TX 20213 pps / 244.82 Mbps (drop 1889)  |  ring depth 0  kernel drops 0  backpressure 1155
```

`drop` and `backpressure` climbed in lockstep, proving that frames read from BPF were being discarded when no free bulk OUT transfer was immediately available.

**③ The TX issue was not caused by RNDIS multi-packet aggregation.**
Testing with `--max-tx-packets` clamped to 1 vs. 3 vs. 10 (the device's reported `MaxPacketsPerMessage=10`) falsified the hypothesis that the device was dropping aggregated packets:

| Packets Aggregated per Transfer | UDP Loss Rate | TCP TX |
|---|---:|---:|
| 1 (clamped) | 42% | 125 Mbps |
| 3 | 43% | 237 Mbps |
| 10 (device-reported default) | 35–58% | 234–241 Mbps |

Clamping to 1 packet per transfer actually halved TCP throughput. Aggregation is effective; the bottleneck was elsewhere (see ②).

### Bidirectional Concurrent TX Previously Collapsed to 4.8 Mbps

Before the fix, each direction performed well in isolation, but under simultaneous bidirectional TCP load:

```
[TX-C]  4.82 Mbits/sec   471 retr   cwnd 11.3 KBytes
[RX-C]  320  Mbits/sec     0 retr
```

TX collapsed to **4.8 Mbps** (~1/50th of unidirectional throughput). The initial hypothesis was **bufferbloat**:

- UDP cross-traffic ruled out USB bus bandwidth contention: injecting 50 Mbps UDP TX alongside saturated RX yielded only **0.32%** TX loss and 348 Mbps combined throughput;
- Saturated RX inflated RTT from **0.4 ms (idle) to 16.6 ms** (40×);
- Because TX ACKs return over the congested RX path, a `cwnd` clamped at 11 KB limits throughput to `11 KB × 8 / 16.6 ms ≈ 5.3 Mbps` — matching the observed 4.8 Mbps.

That arithmetic explained the **symptom**, but the primary cause of `cwnd` being clamped at 11 KB was TX frame drops inside TetherKitNext. Once TX frame drops were eliminated, bidirectional TX jumped from 4.8 Mbps to **87 Mbps** without changing RX queuing depth. **Bufferbloat was a secondary factor, not the root cause.**

## Root Cause and Fix of TX Frame Drops

**Root cause (one line)**: `Bridge::RunTransmitExtractor` **immediately discarded** the remaining frames in a batch whenever the USB bulk OUT transfer pool was full, instead of waiting a few hundred microseconds for a slot to free up.

The earlier code executed `AddDroppedFull(remaining) + break` whenever `SendFrames` returned 0, accompanied by a plausible-sounding but factually wrong comment:

> Deliberately **drop** rather than wait here: waiting would let the kernel BPF buffer build up until the kernel drops packets (invisibly to us). Dropping and counting in user space lets operators see what happened.

Both premises were false:

1. **Kernel drops are not invisible.** Every `BpfLink::ReadFrames` batch queries `BIOCGSTATS` (`bs_drop`) and reports it directly in the "kernel drops" statistic.
2. **Absorbing bursts is the exact purpose of the 4 MiB kernel BPF buffer.** At 250 Mbps, 4 MiB provides ~130 ms of elasticity, whereas a bulk OUT transfer slot frees up in a few hundred microseconds. Refusing to wait even a microsecond discarded bursts in user space that the 4 MiB kernel buffer would have effortlessly absorbed.

The order-of-magnitude mismatch was stark: the device reported `15800 bytes / 10 packets` per transfer, meaning a 256-frame batch slice required **~26 transfer slots**, while the pool only had **4 slots**. Every burst hit backpressure after the 4th slot and immediately dropped the remaining 200+ frames — causing the 30%+ TX packet loss.

**Fix**: `SendFrames` now returns `SendOutcome{consumed, sent_frames, sent_bytes, skipped}`. When `consumed == 0`, the bridge calls `WaitForSendCapacity(50ms)` (woken by a condition variable in the transfer completion callback) and retries after re-checking shutdown/pause flags — **dropping zero frames**. Overflow absorption is delegated back to the kernel BPF buffer, where any real overflow is tracked via `BIOCGSTATS`.

### Results After the Fix (Same Device, Default Settings)

| Metric | Before Fix | After Fix |
|---|---:|---:|
| TetherKitNext TX frame drops (6–8 s window) | 1889 | **0** |
| TCP TX retransmissions | 3829 | **0** |
| TCP TX throughput | 234–241 Mbps | 239–302 Mbps |
| **Bidirectional concurrent TX** | **4.8 Mbps** | **87 Mbps** |
| Bidirectional concurrent RX | 320 Mbps | 240 Mbps |
| Unidirectional TCP RX (regression check) | 324–327 Mbps | 326–327 Mbps |

Two honest observations:

- **Bidirectional RX shifted from 320 to 240 Mbps.** This is a restoration of fairness rather than a regression: before the fix, TX was starved at 4.8 Mbps and RX monopolized the link; now both directions share the bus (`240 + 87 ≈ 327 Mbps` vs. `320 + 4.8 ≈ 325 Mbps`).
- **TCP TX exhibits bimodal behavior** (~240 Mbps vs. ~300 Mbps stable states across repeated runs), both with **zero retransmissions** (not caused by packet loss).

### Corollary: `--tx-transfers` No Longer Needs Tuning

Before the fix, raising in-flight transfers from 4 to 16 cut frame drops to ~1/4 because extra pool depth partially compensated for refusing to wait. Repeating three trials after the fix:

| `--tx-transfers` | TCP TX (3 trials) | Bidirectional TX | TCP RX |
|---|---|---:|---:|
| 4 (default) | 239 / 297 / 241, 0 retransmits | 87.8 / 86.6 | 327 |
| 8 | 298 / 238 / 297, 0 retransmits | 86.9 / 85.7 | 326 |
| 16 | 302 / 302 / 217, 1 retransmit | 86.2 / 89.6 | 326 |

**All three pool depths perform identically within noise.** The default therefore stays at 4 — pool depth only needs to overlap assembling the next batch with the previous batch in flight.

### Debugging Pitfall: Android's `rx_errs` Counter Is Unreliable

On the phone side, `/proc/net/dev` for `rndis0` rapidly increments `rx_errs` / `rx_frame` (sometimes 30–50% of received packets), which is easily misread as "the host is sending malformed frames." **It is not.** A low-rate control test immediately falsifies this:

```
50 pings → 50 replies, 0% packet loss; yet rx_pkts +51 and rx_errs +51 in lockstep
```

Every frame is counted as both received and errored while all replies succeed normally. **When diagnosing TX issues, rely on `iperf3` packet loss and TetherKitNext's own counters, not the phone's `rx_errs`.**

## Measurement Methodology and Caveats

- **Microbenchmark numbers represent hot L1-cache upper bounds.** Real RX buffers written by USB DMA are cold in CPU cache; streaming `memcpy` of 1514 bytes takes 67–71 ns vs. ~33 ns in L1. Treat CPU microbenchmark figures in these tables as **lower bounds** on latency. The link-layer benchmarks (`BPF` / `feth`) are unaffected because they measure real kernel system calls.
- **The historical anomaly where "RNDIS encoding was faster than bare `memcpy`" is gone.** An earlier hardware run recorded ~14 ns/frame for 1514B encoding vs. ~25 ns for `memcpy`. Re-measured on Apple M5, encoding takes 35.1 ns vs. 32.9 ns for `memcpy` — slightly slower than `memcpy`, matching expectations (`memcpy` plus a 44-byte header).
- **High-spread benchmarks** (`SPSC cross-thread`, `FrameRing single-thread 64B`, `feth round-trip latency`) should be evaluated by their **Best ns/op** column because spinning threads can be scheduled across different combinations of Performance and Efficiency cores (4 P + 6 E), and macOS does not support strict core pinning (`thread_affinity_policy` is advisory/ignored on Apple Silicon).
- **Link-layer benchmarks require root.** Running without root skips the group with an explicit note rather than silently omitting it. Re-run with `sudo ./build/bin/tetherkitnext_bench > docs/BENCHMARKS.md`. Note that the fixture must be torn down explicitly before `main` returns (`ShutdownNetBenchmarks`) — leaving teardown to static destructors triggers an abort (exit code 134) because the logging mutex has already been destroyed.
- **Compiler barrier lesson (`ClobberMemory`)**: the statistics counter benchmark initially reported **0.00 ns/op** because back-to-back `memory_order_relaxed` read-modify-writes can be coalesced by the compiler (`N` increments of `+1` folded into a single `+N`). Adding `ClobberMemory` revealed the true 0.34 ns/op cost.

## ⚠️ Benchmark Environment Pitfall: Privilege Escalation Swallows SIGTERM

The `osascript ... with administrator privileges` privilege-escalation chain **swallows inter-process `SIGTERM` delivery**: `kill -TERM $pid` returns 0, the target process's `blocked` and `pending` signal masks remain 0, and `sigaction` shows the handler installed, yet the signal never arrives and the process can only be terminated with `kill -9`.

Verified with a standalone 15-line C reproduction independent of TetherKitNext:

| Execution Environment | Receives `SIGTERM`? |
|---|---|
| Standard interactive shell | ✅ |
| Standard `osascript do shell script` | ✅ |
| `osascript ... with administrator privileges` | ❌ |

**Consequence: never use `osascript ... with administrator privileges` to test graceful shutdown.** It produces a false "shutdown hang" (`Killed: 9`) unrelated to the application code. Always verify graceful shutdown in a real interactive terminal via `sudo build/bin/tetherkitnext-cli` followed by `Ctrl-C`.
